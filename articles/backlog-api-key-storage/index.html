Backlog APIキーをChrome拡張で安全に保存する仕組み

APIキーを入力する拡張機能では、「暗号化している」という説明だけでなく、どこに保存し、どこへ送信し、利用中はどう扱うかが重要です。IssueDockの保存設計を例に、確認すべき仕組みを整理します。

CONTENTS

APIキーは接続のための認証情報 パスフレーズから鍵を作って暗号化する 暗号文と復号済みキーを分けて扱う 保存先へのアクセスと送信先を確認する IssueDockのデータの扱いを確認して使う

01 / GUIDE

APIキーは接続のための認証情報

Backlog APIの認証方式は公式の認証と認可ドキュメントにまとめられています。APIキーは課題へアクセスするための認証情報なので、共有メモや問い合わせ文へ貼り付けないようにします。

保存時、端末間で同期するとき、APIへ送るときでは守り方が異なります。保存データを暗号化していても、通信に利用する時点では拡張機能がキーを復号する必要があります。

02 / GUIDE

パスフレーズから鍵を作って暗号化する

IssueDockはPBKDF2-SHA-256でパスフレーズから暗号鍵を導出し、AES-256-GCMでAPIキーを暗号化します。暗号文と復号に必要なパラメーターを保存し、同期用パスフレーズ自体は保存しない設計です。

パスフレーズは他のサービスと使い回さず、推測されにくいものを選びます。暗号化しても、短く単純なパスフレーズや感染した端末まで安全にできるわけではありません。

03 / GUIDE

暗号文と復号済みキーを分けて扱う

Chrome Storageの公式仕様では、端末内のlocal、端末間で同期するsync、メモリ上のsessionが区別されています。保存場所の名前だけで秘密情報の保護が完了するわけではありません。

  • IssueDockのAPIキー：暗号化した接続情報として保存します。Chrome同期を選ぶと、暗号文を同期します。
  • 復号済みAPIキー：保存方法に応じてchrome.storage.localまたはchrome.storage.sessionで扱い、同期しません。
  • 同期用パスフレーズ：保存せず、同期にも含めません。
  • 課題キャッシュ：Chrome拡張のIndexedDBに保存します。

「平文を同期しない」と「端末上に平文が存在しない」は異なります。localに復号済みキーを保存する場合は端末に残るため、共有PCや端末管理の条件も考慮して保存方法を選びます。

04 / GUIDE

保存先へのアクセスと送信先を確認する

IssueDockはChrome Storageへのアクセスを拡張の信頼されたコンテキストへ制限し、接続するBacklogスペースごとにサイト権限を要求します。課題・APIキー・個人整理データを運営者のサーバーへ送信しない設計です。

一方、アカウント認証や契約管理のための通信は存在します。データの種類と目的を分けて確認することが大切です。現在の保存先・外部通信・削除方法はプライバシーポリシーで確認できます。

APIキーが漏れた可能性がある場合は、暗号化保存し直すだけでは解決しません。Backlog側でキーを無効化・再発行し、接続情報も更新します。不要な接続は解除し、ログやスクリーンショットにキーを残さないようにします。

05 / GUIDE

IssueDockのデータの扱いを確認して使う

IssueDockは、Backlogの課題を横断して個人整理するためのChrome拡張です。便利さだけでなく、端末内の保存、暗号文の同期、利用中の復号済みキーという違いを理解したうえで、所属組織のルールに合うか確認してください。

導入時の操作や問い合わせ先はサポートページにまとめています。問い合わせにはAPIキーやパスフレーズを含めないでください。
